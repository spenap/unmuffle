<task type="checkpoint:human-action" gate="blocking">
  <name>Task 1: Configure GitHub Actions secrets for release signing</name>
  <action>
The user must configure 4 secrets in the GitHub repository settings for release signing to work.

**If you do not already have a release keystore**, generate one:
```bash
keytool -genkeypair -v -keystore release.keystore -alias transchat -keyalg RSA -keysize 2048 -validity 10000 -storepass YOUR_STORE_PASSWORD -keypass YOUR_KEY_PASSWORD -dname "CN=Simon Pena, O=TransChat"
```

**Encode the keystore to base64:**
```bash
base64 -w 0 release.keystore
```

**Navigate to:** GitHub repo > Settings > Secrets and variables > Actions > New repository secret

**Add these 4 secrets:**

| Secret Name | Value |
|-------------|-------|
| `KEYSTORE_BASE64` | The base64-encoded content of your release .keystore file (output of `base64 -w 0 release.keystore`) |
| `KEYSTORE_PASSWORD` | The store password used when creating the keystore |
| `KEY_ALIAS` | The key alias (e.g., `transchat`) |
| `KEY_PASSWORD` | The key password used when creating the keystore |

**Important:** Do NOT commit the .keystore file to the repository. Store it securely offline as a backup. The base64-encoded version in GitHub secrets is the only way CI accesses it.
  </action>
  <verify>
    <automated>gh secret list 2>/dev/null | grep -c "KEYSTORE_BASE64\|KEYSTORE_PASSWORD\|KEY_ALIAS\|KEY_PASSWORD" | grep -q "4" && echo "PASS" || echo "FAIL — configure secrets in GitHub repo settings or install gh CLI and authenticate"</automated>
  </verify>
  <done>Four GitHub Actions secrets are configured: KEYSTORE_BASE64, KEYSTORE_PASSWORD, KEY_ALIAS, KEY_PASSWORD.</done>
</task>

<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 2: Verify split CI pipeline on GitHub (push + tag)</name>
  <action>
Verify the split CI pipeline works end-to-end: fast path on push to main, full pipeline on tag push.

GitHub Actions CI pipeline from Plan 09-01 (workflow file + signing config) with secrets from Task 1.

**Part A — Verify fast path (push to main):**
1. Push the branch to GitHub (if not already pushed):
   ```bash
   git push origin main
   ```
2. Go to the repository on GitHub > Actions tab
3. Verify the "Build" workflow was triggered
4. Wait for the workflow to complete
5. Check these items:
   - **Lint step** passed (no lint errors)
   - **Debug build** step passed
   - **Release build** step was SKIPPED (not run)
   - **Artifact upload** steps were SKIPPED (not run)
   - **No artifacts** section on the completed workflow run

**Part B — Verify full pipeline (tag push):**
1. Create and push a tag:
   ```bash
   git tag v1.2.0-rc1
   git push origin v1.2.0-rc1
   ```
2. Go to the repository on GitHub > Actions tab
3. Verify a new "Build" workflow run was triggered by the tag push
4. Wait for the workflow to complete (expect 5-15 minutes due to native C++ compilation)
5. Check these items:
   - **Lint step** passed
   - **Debug build** step passed
   - **Release signing** step ran (not skipped)
   - **Release build** step passed
   - **Artifacts section** shows two downloadable artifacts: `app-debug` and `app-release`
6. Download the `app-release` artifact and verify it contains a signed APK (not debug-signed):
   ```bash
   # After downloading and unzipping the artifact:
   apksigner verify --print-certs app-release-unsigned.apk 2>/dev/null || apksigner verify --print-certs app-release.apk
   ```
   The signer should show your release certificate CN, not the Android debug certificate.

**If the workflow fails:**
- Check the workflow run logs on GitHub Actions for the failing step
- Common issues: NDK/CMake version mismatch, submodule checkout failure, missing secrets
- Report the failing step and error message

Type "approved" if both parts pass (push = fast path, tag = full pipeline with artifacts), or describe the failure.
  </action>

  </verify>

</task>
